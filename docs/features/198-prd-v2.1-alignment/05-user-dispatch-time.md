# PRD v2.1 / 05: 사용자별 알림 발송 시각

상태: 구현 및 검증 완료 (2026-10-19)

## 목표와 변경 전 구조

`dispatchTime` 기본값은 09:00으로 유지하고, 사용자가 `PUT /notifications/settings`로 변경한 값을 실제 자동 발송에 적용한다.
기존 API와 00:00~23:30의 30분 단위 검증을 유지한다. 세 유형의 알림은 공통 시각 하나를 쓴다.

변경 전 `NotificationSchedulerService`는 매일 09:00에 `dispatch()`를 호출한다. `NotificationPolicyService`는 날짜·유형별 후보를 계산하고,
`NotificationDispatchService`는 사용자별로 묶어 전송한 뒤 알림함과 소모품 발송 상태를 저장한다.
`dispatchTime`은 이미 DB에 저장되지만 발송에 쓰이지 않는다. 사전·당일 알림은 발송 상태가 없어 배치 반복 실행 시 중복된다.

## 동작 규칙

- 스케줄러 기본 cron을 `0 * * * * *`로 바꿔 매분 실행한다. 기존 전역 자동 발송 스위치와 유형별 킬 스위치는 유지한다.
- `notification.schedule.zone`(기본 `Asia/Seoul`)을 날짜·시각 판정에도 동일하게 적용한다. 사용자별 시간대 설정은 추가하지 않는다.
- 실행 시작 시각을 한 번 읽고 해당 날짜의 정책 후보를 계산한다. 사용자 설정은 일괄 조회한다.
- 자동 발송 대상은 `현재 시각 >= 저장된 dispatchTime`이고 해당 날짜에 아직 발송을 완료하지 않은 사용자다.
- 발송 완료는 푸시 성공 또는 등록 기기 없음이다. 기기가 없어도 기존 동작처럼 알림함에 남기고 완료 처리한다.
- 대상 소모품이 없으면 완료일을 기록하지 않는다. 이후 같은 날 대상이 생기면 발송할 수 있다.
- 사용자별 소모품은 한 푸시로 묶는다. 사용자당 정책 알림은 하루 한 번이며 발송 이후 추가한 소모품은 당일 다시 보내지 않는다.
- 실패하면 알림함·소모품 상태·발송 완료일을 기록하지 않고 다음 분에 재시도한다. 날짜가 바뀌면 새 날짜의 후보만 계산한다.
- 같은 날 서버가 재시작되거나 cron이 반복 실행돼도 DB의 완료일로 중복을 막는다.

### 시간 변경 예시

| 상황 | 처리 |
| --- | --- |
| 기본 09:00, 현재 08:59 | 보내지 않고 09:00 이후 첫 실행에서 발송 |
| 08:00에 09:00 → 18:30 변경 | 오늘 18:30 이후 발송 |
| 아직 미발송, 10:00에 09:00 → 08:30 변경 | 다음 분 실행에서 오늘 후보 발송 |
| 오늘 09:00 발송 완료 후 18:30으로 변경 | 오늘 추가 발송 없이 내일 18:30부터 반영 |
| 서버 중단으로 설정 시각을 놓쳤으나 같은 날 복구 | 다음 실행에서 당일 미발송 건 처리 |
| 자정 이후 복구 | 어제 사전·당일 알림은 보내지 않음. 지연 알림의 기존 따라잡기 규칙 유지 |

설정 변경은 다음 배치가 읽는 최신 저장값부터 적용한다. 이미 진행 중인 전송은 취소하지 않는다.

## 저장과 서비스 변경

- `V15__add_last_notification_dispatch_date.sql`: `user_notification_settings.last_dispatch_date DATE NULL` 추가.
  기존 `dispatch_time`과 토글은 보존하고 완료일 초기값은 NULL로 둔다. 과거 알림함 행에서 완료일을 추정하지 않는다.
- `UserNotificationSettings`와 `EffectiveNotificationSettings`에 `lastDispatchDate`를 추가한다. API 요청·응답에는 노출하지 않는다.
- 완료일은 알림함 저장·소모품 상태 갱신과 같은 트랜잭션에서 저장한다. 설정 변경과 같은 사용자 잠금을 써서 서로 덮어쓰지 않게 한다.
- 기존 단일 인스턴스 `dispatchLock`을 자동·수동 발송이 공유한다. 다중 인스턴스 실행과 푸시 성공 직후 DB 저장 실패에 대한 정확히 한 번 보장은 이번 범위 밖이다.
- 날짜별 정책 판정에 실행 시작 날짜를 전달한다. 서버 OS 시간대와 스케줄 설정 시간대가 달라도 발송 날짜가 일치해야 한다.
- `data.sql`은 설정 행을 넣지 않으므로 추가 시드 없이 새 컬럼에 대한 주석만 갱신한다. H2는 엔티티의 nullable 컬럼을 자동 생성한다.

## 어드민과 API 문서

- 자동 발송 안내에 사용자별 시각과 매분 확인을 명시한다.
- 수동 `지금 배치 실행`은 사용자 시각과 자동 발송 스위치를 무시하되 당일 중복 방지는 동일하게 적용한다.
- 미리보기는 수동 실행 기준이다. 사용자 시각을 무시하고 오늘 이미 완료한 사용자를 제외한다. 공지 발송은 이 제한의 대상이 아니다.
- DTO·Swagger의 '저장만', '09:00 일괄' 설명을 실제 동작과 기본값으로 수정한다.

## 검증과 완료 기준

- 고정 Clock으로 08:59/09:00, 30분 슬롯, 서로 다른 사용자 시각, 00:00/23:30과 시간대 차이를 검증한다.
- 시간 변경 전후와 동일 날짜 반복 호출에서 한 번만 발송하고 다음 날에는 다시 발송한다.
- 동일 DB를 쓰는 새 서비스 인스턴스도 오늘 완료한 사용자를 재발송하지 않는다.
- 실패 후 완료일이 남지 않고 다음 실행에서 재시도되며, 기기가 없으면 완료일과 알림함이 함께 저장된다.
- 수동 발송과 미리보기, 자동 발송 스위치, 유형별 토글 동작을 회귀 검증한다.
- Flyway 마이그레이션으로 기존 사용자 시각과 설정값이 보존되는지 확인하고 `gradlew.bat harness`를 실행한다.
