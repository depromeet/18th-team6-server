# PRD v2.1 정합화: 설계 초안

- 작성일: 2026-10-17
- 이슈: #198
- 범위: PRD v2.0 → v2.1 Changelog 중 서버 변경이 필요한 항목. 단계별 스펙은 `docs/features/198-prd-v2.1-alignment/`에 둔다.

## 1. 목표와 전제

- 서버 동작을 PRD v2.1(온보딩·추가·상세·알림 기능명세서 반영본)에 맞춘다.
- 기존 사용자가 받던 알림과 등록해 둔 소모품 데이터는 바뀐 규칙 때문에 사라지거나 갑자기 달라지지 않게 한다.
- 기존 API 경로와 `Category` 계열 이름은 유지한다. 클라이언트가 고칠 범위를 신규 필드와 삭제 필드로 한정한다.
- 운영 DB 스키마는 Flyway(`src/main/resources/db/migration`, 현재 V11)로 바꾸고, 로컬 H2 시드 `data.sql`도 함께 고친다.
- 기본 소모품 목록과 카테고리 데이터는 기획에서 표를 받아 사용자가 운영 DB에 직접 넣는다. 서버 작업은 저장 구조까지다.

### 용어 대응

| PRD v2.1 | 코드 | 테이블 |
| --- | --- | --- |
| 소모품 (예: 칫솔) | `Category` | `categories` |
| 사용자 소모품 | `Category` 중 `userId != null` | `categories.user_id` |
| 내 소모품 | `Item` | `items` |
| 카테고리 (욕실·주방 등) | `CategoryGroup` (신규) | `category_groups` (신규) |

신규 이름은 `ItemGroup` 대신 `CategoryGroup`으로 한다. 묶는 대상이 `Item`이 아니라 `Category`이기 때문이다.

## 2. 확정한 결정

| 항목 | 결정 |
| --- | --- |
| 마지막 교체 시점 | 상대 구간 선택(`LastReplacementPeriod`) 삭제. 모든 등록 경로에서 등록일을 마지막 교체일로 쓴다. 상세 편집에서 마지막 교체일은 읽기 전용 |
| 사용자 소모품 | 기본 주기 90일, 공용 아이콘. 삭제 API(`DELETE /categories/{id}`)는 그대로 둔다 |
| 영수증 등록 | 새로 인식된 소모품은 사용자 소모품 규칙(90일, 공용 아이콘)을 따른다 |
| 카테고리 | 온보딩 목록을 카테고리 탭으로 나눈다. 소모품 하나는 카테고리 하나에만 속한다 |
| 사용자 소모품의 카테고리 | '사용자' 카테고리 하나에 자동으로 속한다. 사용자가 카테고리를 만들거나 고르지 않는다 |
| 온보딩 진입 판단 | 앱이 기존 API 응답으로 판단한다. 서버 변경 없음 |
| 관리 대상 한정 | 소진형 제외는 기본 소모품 데이터 수동 갱신으로 처리한다 |
| 알림 설정 | 유형별 토글 3개와 공통 알림 시간 하나. 전체 토글·선행 일수·조용 시간 제거 |
| 토글 기본값 | 새 사용자만 세 유형 모두 꺼짐. 기존 사용자는 지금 받던 상태 유지 |
| 발송 시각 | 현행 유지. 전 사용자 매일 09:00 일괄 발송. 저장된 알림 시간은 발송에 쓰지 않는다 |
| 알림 일정 | 사전 D-7·D-3·D-1, 당일, 지연 D+1·D+3·D+7 |
| 여분 부족 조건 | 현행 유지. 여분 0(미입력 제외), 교체일까지 3일 이하, 재입고 전 1회. 3일은 고정값 |
| 복수 사유 | 같은 날 같은 소모품의 일정 사유와 여분 부족을 한 알림으로 합친다. 각 사유는 자기 토글을 따른다 |
| 묶음 알림 | 현행 유지. 사용자당 푸시 1건, 소모품 여럿이면 홈으로 이동 |
| 앱 내부 알림함 | 기존 구현 유지 |
| 당일 알림의 토글 | '교체 예정' 토글을 따른다 |
| 구버전 앱 호환 | 알림 설정 `GET` 응답에 `enabled`, `leadDays`를 고정값(`true`, `3`)으로 한동안 남기고 다음 배포에서 삭제 |
| 알림 문구 | 04의 문구를 쓴다. 기능명세서에 문구가 생기면 그걸 따른다 |

## 3. 저장소에서 확인한 현재 상태

| 영역 | 현재 구현 | v2.1과의 차이 |
| --- | --- | --- |
| 소모품 등록 | `CreateItemRequest.lastReplacementPeriod`로 4·21·45·90일 전을 마지막 교체일로 저장 (`ItemService.saveItem`) | 구간 선택 삭제, 항상 오늘 |
| 상세 편집 | `PATCH /items/{id}`가 이름·여분·교체 주기·`lastReplacedDate`를 받는다 | `lastReplacedDate` 수정 불가 |
| 사용자 소모품 생성 | `POST /categories`는 `iconId` 필수, 주기는 엔티티 기본값 1일. `POST /items`의 `newCategoryName` 경로는 `newCategoryDefaultReplacementIntervalDays ?: 1` | 90일, 공용 아이콘 |
| 영수증 | 매칭 실패 소모품의 `suggestedReplacementIntervalDays`는 OCR 추천값(없으면 1) | 90일 |
| 카테고리 | 없음. `GET /categories`는 프리셋과 사용자 소모품을 한 목록으로 준다 | 신규 |
| 사용자 알림 설정 | `enabled`, 유형 토글 3개(기본 켜짐), `leadDays`(1~7), `dispatchTime`(08:00~21:30, 30분 단위). 행이 없는 사용자는 모두 켜짐으로 판정 | 전체 토글·선행 일수·시간 제한 제거, 신규 사용자 기본 꺼짐 |
| 전역 알림 설정 | `notification_settings` 단일 행. `lead_days`, `overdue_step_days`('1,4,7'), 유형별 킬 스위치, 자동 발송 스위치. 어드민 화면에서 수정 | 사전 스텝 목록과 여분 부족 기준으로 재구성 |
| 알림 판정 | 소모품마다 `OVERDUE > LOW_STOCK > PRE_REPLACEMENT` 중 하나만 고른다. 사전은 `daysUntil == leadDays` 1회 | 일정 7회, 사유 결합 |
| 알림 발송 | 사용자당 푸시 1건, 알림함에 `Notification` 1행. 전송 실패 시 상태 미확정 | 유지 |

## 4. 변경 설계 요약

세부는 각 스펙에 적는다.

1. **소모품 등록·편집** ([01](../features/198-prd-v2.1-alignment/01-item-registration.md)): 구간 선택 삭제, 마지막 교체일 읽기 전용, 사용자 소모품 90일·공용 아이콘, 영수증 추천 주기 정리.
2. **카테고리** ([02](../features/198-prd-v2.1-alignment/02-category-group.md)): `category_groups` 테이블과 `categories.category_group_id`, 탭 목록 API, 사용자 소모품의 '사용자' 카테고리 자동 배정.
3. **알림 설정** ([03](../features/198-prd-v2.1-alignment/03-notification-settings.md)): 사용자 설정 단순화, 기존 사용자 상태 보존 마이그레이션, 신규 사용자 기본 꺼짐.
4. **알림 일정과 사유 결합** ([04](../features/198-prd-v2.1-alignment/04-notification-schedule.md)): 사전·당일·지연 스텝, 여분 부족 결합, 문구와 라벨, 어드민 설정 화면.

## 5. 스펙 분할과 순서

| 순서 | 스펙 | 주요 산출물·완료 기준 |
| --- | --- | --- |
| 1 | 01 소모품 등록·편집 | 모든 등록 경로가 오늘을 마지막 교체일로 저장. 사용자 소모품 주기 90일. 기존 테스트 갱신 |
| 2 | 02 카테고리 | 스키마 마이그레이션, 탭 목록 API, `GET /categories` 응답에 카테고리 필드. `data.sql` 갱신 |
| 3 | 03 알림 설정 | 설정 API 필드 정리, 마이그레이션 후 기존 사용자 판정 결과가 이전과 같음을 테스트로 확인 |
| 4 | 04 알림 일정과 사유 결합 | 일정 7회와 결합 문구 판정 테스트, 어드민 설정·미리보기 반영 |

01과 02는 서로 독립이다. 04는 03의 설정 구조를 읽으므로 03 다음에 한다.
배포는 앱 v2.1 출시와 맞춘다. 설정 API에서 필드가 빠지므로 구버전 앱과의 호환 범위를 03에 적는다.

## 6. 범위 밖

- 사용자별 알림 시간에 맞춘 발송 (필요해지면 별도 결정)
- 사용자 소모품 수정 (PRD 후속 과제)
- 기본 소모품·카테고리 데이터 입력과 소진형 소모품 정리 (사용자가 운영 DB에 직접 반영)
- `Category` → `Consumable` 등 전체 리네이밍
- NSM 분모 산출 (PRD OQ-04 미결)
- 가설 검증 비교군: 유형 토글과 OS 권한 상태는 이미 `user_notification_settings`에 저장되므로 서버 변경 없음
- 이미 1일 주기로 만들어진 기존 사용자 소모품과 내 소모품의 주기 보정

## 8. 제 판단으로 정한 것

구현 전에 확인해 주면 좋은 항목이다.

- 신규 이름 `CategoryGroup` (1장)
- 기존 사용자 보존 방식: 마이그레이션 때 모든 기존 사용자에게 지금 상태(켜짐)를 행으로 기록하고, 행이 없으면 꺼짐으로 판정 (03)
- 전체 토글을 꺼둔 기존 사용자는 세 유형을 모두 꺼짐으로 옮김 (03)
- 알림 시간의 08:00~21:30 제한 제거, 30분 단위는 유지 (03)
- 사전·당일 알림은 따라잡기 없이 그날에만 발송 (04)
- 진행 중인 지연 알림은 새 스텝(1,3,7)으로 그대로 이어감. 어드민에서 바꾼 값은 유지 (04)
- 여분 부족 기준 3일은 전역 값으로 두고 어드민에서만 바꿈 (04)
- 결합 알림의 알림함 유형은 일정 사유 우선, 없으면 여분 부족 (04)
- `POST /categories`의 `iconId`는 받아도 무시 (01)
- '사용자' 카테고리 행이 없으면 소모품 등록은 막지 않고 카테고리를 비워 둠 (02)
