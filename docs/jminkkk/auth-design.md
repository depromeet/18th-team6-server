## 1. 개요

현재는 개인 소모품 관리 앱이나, 추후 소셜 기능 확장 가능성을 고려해 인증 구조를 갖춘다.

구현 디테일보다 **설계 결정과 그 근거**를 중심으로 기술한다.

### 현재 서비스 규모 가정

- 팀 규모: 10명 (백엔드 3명)
- 플랫폼: 모바일 앱 (B2C)
- 소셜 기능: 현재 없음, 추후 확장 가능성 있음

## 2. 인증 방식

### 검토된 대안

|  | 세션 | JWT (stateless) | JWT + Redis |
| --- | --- | --- | --- |
| 구조 | 서버가 상태 보관 | 토큰 자체에 정보 | JWT + 서버 검증 |
| 규모 확장 | 서버 증가 시 세션 공유 문제 | 수평 확장 자유로움 | 수평 확장 자유로움 |
| 토큰 무효화 | 즉시 가능 | 불가 (만료 전까지) | 즉시 가능 |
| 복잡도 | 낮음 | 낮음 | 중간 |

### 규모별 판단

- **초기 (서버 1~2대)**: 세 가지 모두 가능
- **성장기 (서버 증가)**: 세션은 sticky session 또는 Redis 세션 저장소 필요 → 결국 Redis 도입
- **토큰 강제 만료 필요 시** (탈퇴, 비밀번호 변경, 보안 이슈): JWT 단독으로는 불가

### 결정: **JWT + Redis**

B2C 앱에서 강제 로그아웃(탈퇴, 기기 변경)은 필수 요구사항이다.
초기에 오버스펙처럼 보이더라도, 나중에 추가하면 마이그레이션 비용이 더 크다.

### 팀 결정 필요

- Redis 운영 부담 감수 여부

## 3. 소셜 로그인 연동

### OAuth 플로우 검토

|  | Authorization Code | Implicit | 백엔드 대리 처리 |
| --- | --- | --- | --- |
| 흐름 | 클라이언트 → 백엔드 → OAuth 서버 | 클라이언트 → OAuth 서버 직접 | 백엔드가 전체 처리 |
| 보안 | 높음 (토큰 노출 없음) | 낮음 (토큰 URL 노출) | 높음 |
| 복잡도 | 중간 | 낮음 | 중간 |
| 현재 표준 여부 | ✅ | ❌ (deprecated) | ✅ |

### 결정: **Authorization Code Flow**

Implicit은 토큰이 URL에 노출되어 브라우저 히스토리, 서버 로그, 리퍼러 헤더에 남는다.
현재 OAuth 표준에서 deprecated 처리됨.

> 모바일 앱 환경에서는 **PKCE(Proof Key for Code Exchange)** 적용 권장.
PKCE는 Authorization Code를 중간에 탈취당해도 원본 verifier 없이는 교환 불가한 보안 확장이다.
클라이언트 팀과 별도 협의 필요.
>

### 계정 연계 전략 검토

> "카카오로 가입했는데 이메일로도 로그인하고 싶다"
>

|  | 이메일 기준 자동 연계 | 명시적 연계 (사용자가 직접) | 연계 미지원 |
| --- | --- | --- | --- |
| UX | 자연스러움 | 명확함 | 단순함 |
| 보안 리스크 | 이메일 도용 가능성 | 없음 | 없음 |
| 구현 복잡도 | 높음 | 중간 | 낮음 |

### 결정: **명시적 연계** (초기 미지원 후 추가 가능)

자동 연계는 보안 리스크 대비 UX 이득이 크지 않다.
명시적 연계는 복잡도와 보안 사이 균형점이며, 초기에는 미지원으로 두고 수요 확인 후 추가한다.

### 팀 결정 필요

- 초기 계정 연계 지원 여부

## 4. 토큰 전략

### 클라이언트 저장 위치 검토

|  | LocalStorage | Cookie (httpOnly) | Memory (변수) |
| --- | --- | --- | --- |
| XSS 취약성 | 높음 (JS 접근 가능) | 없음 | 없음 |
| CSRF 취약성 | 없음 | 있음 (대응 필요) | 없음 |
| 탭 간 공유 | 됨 | 됨 | 안 됨 |
| 새로고침 후 유지 | 됨 | 됨 | 안 됨 |

### 결정: **httpOnly Cookie**

XSS는 프론트 실수 한 번으로 터지는데, LocalStorage는 그 순간 토큰이 그대로 노출된다.
httpOnly Cookie는 JS 접근 자체가 차단되며, CSRF는 SameSite 설정으로 대응 가능하다.

### 갱신 전략 검토

|  | 만료 시 재로그인 | Refresh Token | RTR (Refresh Token Rotation) |
| --- | --- | --- | --- |
| UX | 나쁨 | 좋음 | 좋음 |
| 보안 | 높음 | 중간 | 높음 |
| 구현 복잡도 | 낮음 | 중간 | 중간 |
| 탈취 대응 | - | 탈취 시 만료까지 속수무책 | 탈취 즉시 감지 가능 |

**RTR 동작 방식**

```
Refresh Token 사용 시 → 새 Refresh Token 발급 + 기존 즉시 폐기
탈취된 토큰으로 요청 오면 → 이미 폐기됐으므로 감지 가능
→ 해당 유저 전체 세션 강제 만료
```

### 결정: **RTR (Refresh Token Rotation)**

Refresh Token 단독은 탈취 시 만료까지 대응 불가하다.
RTR은 복잡도 차이가 크지 않은 반면 보안은 확연히 올라간다.
2번에서 선택한 JWT + Redis와 자연스럽게 연결된다.

### 팀 결정 필요

- Access Token 만료 시간 (짧을수록 안전 / 길수록 UX 좋음, 권장 범위: 15분~1시간)

## 5. 권한 모델

### 검토된 대안

|  | 단순 Role | Role + Permission | ABAC |
| --- | --- | --- | --- |
| 구조 | USER / ADMIN | Role에 세부 권한 부여 | 속성 기반 동적 판단 |
| 예시 | ADMIN이면 전체 접근 | ADMIN도 권한별 제한 가능 | 시간/위치/상태 조건 가능 |
| 복잡도 | 낮음 | 중간 | 높음 |
| 적합한 규모 | 초기 | 성장기 | 엔터프라이즈 |

### 규모별 판단

- 현재: 사용자가 자기 데이터만 접근, 관리자가 전체 접근 → USER / ADMIN으로 충분
- 성장기: "특정 유저만 베타 기능 접근" 등 수요 발생 시 Role + Permission으로 마이그레이션 가능

### 결정: **단순 Role (USER / ADMIN)**

초기에 복잡한 권한 모델을 만들면 관리 비용만 올라간다.
Role + Permission 마이그레이션은 나중에도 어렵지 않다.

### 팀 결정 필요

- ADMIN 외 추가 Role 필요 여부 (운영자, 베타유저 등)

## 6. 보안 정책

### 토큰 탈취 대응

4번에서 RTR을 선택했으므로 자동으로 탈취 감지 및 세션 강제 만료가 가능하다.
별도 대응 메커니즘 불필요.

### CORS

- 전체 허용() 대신 **화이트리스트** 방식 적용
- 허용 도메인 명시, 복잡도 차이 없음

### CSRF

- 4번에서 httpOnly Cookie를 선택했으므로 `SameSite=Strict` 설정으로 대응 가능
- 설정 한 줄 추가로 해결, 별도 CSRF Token 불필요

### 비밀번호 정책

|  | MD5/SHA | bcrypt | bcrypt + pepper |
| --- | --- | --- | --- |
| 레인보우 테이블 | 취약 | 안전 | 안전 |
| DB 단독 탈취 시 | 취약 | 취약 | 안전 (pepper는 서버에만 존재) |
| 복잡도 | 낮음 | 낮음 | 중간 (키 관리 필요) |

**결정: bcrypt**

업계 표준. 레인보우 테이블, 브루트포스 대응 충분하다.
pepper는 초기 서비스 규모에서 오버스펙이며, 키 rotation 등 운영 부담이 생긴다.
보안 감사 시점에 재검토한다.

### 팀 결정 필요

- 비밀번호 복잡도 정책 (최소 길이, 특수문자 필수 여부 등)

## 7. 예외 처리 / UX 흐름

### 인증 실패 응답

|  | 상세 메시지 | 통일된 메시지 |
| --- | --- | --- |
| 예시 | "비밀번호가 틀렸습니다" | "이메일 또는 비밀번호가 올바르지 않습니다" |
| 보안 | 낮음 (계정 존재 여부 노출) | 높음 |
| UX | 좋음 | 약간 불편 |

**결정: 통일된 메시지**

계정 존재 여부 노출은 공격자에게 정보가 된다.

### 토큰 만료 시 UX 흐름

|  | 즉시 로그아웃 | Silent Refresh → 실패 시 로그아웃 |
| --- | --- | --- |
| UX | 나쁨 | 자연스러움 |
| 구현 복잡도 | 낮음 | 중간 |

**결정: Silent Refresh → 실패 시 로그아웃**

Access Token 만료 시 사용자 모르게 Refresh Token으로 갱신한다.
Refresh Token도 만료됐을 때만 로그아웃 처리한다.
B2C에서 갑자기 튕기는 UX는 이탈 원인이 된다.

### HTTP 상태코드 규격

| 상황 | 결정 |
| --- | --- |
| 인증 실패 (토큰 없음 / 만료) | 401 |
| 권한 없음 (토큰은 유효, 접근 불가) | 403 |
| 잘못된 요청 | 400 |

### 팀 결정 필요

- 프론트엔드와 에러 코드 / 에러 메시지 포맷 합의
